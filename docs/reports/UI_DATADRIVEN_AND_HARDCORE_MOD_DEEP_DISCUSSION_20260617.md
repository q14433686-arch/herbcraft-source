# UI 数据驱动改造 + 硬核模组方向深度讨论

日期: 2026-06-17  
状态: 讨论/设计稿 — 本轮无代码变更  
基线: Herbcraft `1.1.3`, Minecraft `26.1.2`

---

## 第一大问题：UI 能不能改成数据驱动？

### 回答：能，而且应该分三层来做

现在的 UI 是纯 Java 硬编码的——颜色、尺寸、位置、行高全写死在 `CodexScreen.java` 和 `NutritionPanelScreen.java` 里。这意味着：

- 换个颜色要改 Java 重新编译
- 不同分辨率/缩放下表现不可控
- 附属模组/资源包无法覆盖 UI 风格
- 加一个维度就要改面板代码

**推荐的数据驱动 UI 架构分三层：**

#### 第一层：UI 主题配置文件（最低成本，最高回报）

#### 第三层：布局描述器（高成本，暂时不需要）

完整的声明式 UI 布局（类似 Minecraft 自己的 Screen 描述或 web 的 flexbox）——这需要一个小的布局引擎。**1.2.0 不需要做到这一步。** 前两层就够用了。

### 推荐实施顺序

| 步骤 | 内容 | 版本 |
|---|---|---|
| 1 | `codex_theme.json` + `nutrition_theme.json` — 只提取常量 | 1.2.0 |
| 2 | 资源包可覆盖主题文件 | 1.2.0 |
| 3 | Codex 条目详情页组件化（item icon、nature bar、claim 行） | 1.2.0 |
| 4 | 附属模组可以注册新的维度颜色/图标到 nutrition_theme | 1.2.0 |
| 5 | 声明式布局引擎（如果未来真的需要） | 1.3.0+ |

**关键改动：**

4. **面包屑导航** — 标题栏下方显示 `百草志 > 花卉志 > 蒲公英`，点击可回溯。

## 第三大问题：硬核模组到底是什么定位？

### 你的核心问题我理解是这样的：

> "它到底应该叫硬核营养学（只拓展营养），还是硬核模组（一个完整的硬核生存系统）？如果是后者，它还算百草可食的附属吗？"

### 我的分析：三种架构模式

#### 模式 A：纯附属（`herbcraft_hardcore_nutrition`）

```
百草可食 Core  ←───依赖──── 硬核营养学
                            - 更严格的营养规则
                            - 更多维度
                            - 更强的 debuff
```

**优点：** 复用 Core 的全部营养/药理/图鉴代码。
**缺点：** 如果要加体温、水分、医疗，这些东西不属于"营养学"，逻辑上不该由这个附属负责。而且你说了"附属又是别的模组的核心"——这不对。

#### 模式 B：独立硬核模组 + 兼容层（推荐）

```
百草可食 Core ←──可选兼容──→ 硬核生存 Core
  (草药/药理/图鉴)            (体温/水分/营养/医疗)
       ↑                          ↑
  百草可食 Cuisine          硬核生存 草药医疗桥
  百草可食 Alchemy          (把百草可食的药性接入
                             硬核生存的医疗系统)
```

**名字建议：**
- 独立核心模组名：`严生` / `Harsh Survival` / `严律求生` / `求生严律`
- Mod ID: `harsh_survival` 或 `yansheng`
- 百草可食桥接附属：`herbcraft_harsh_bridge`

**优点：**
- 独立模组有自己的身份和发展空间
- 和百草可食的关系是"兼容"而非"依赖"——有百草可食更好，没有也能独立运行
- 体温/水分/医疗是独立的生存维度，不应该被绑死在草药系统上
- 代码可以复用百草可食的营养计算模式（五维→N维），但 UI 和效果系统独立
- 未来可以接入其他食物模组，不限于百草可食

**缺点：** 需要维护两个独立模组和一个桥接层。但这其实是正确的模块化。

#### 模式 C：把百草可食 Core 拆分为"库" + "内容"

```
百草可食 Lib (维度系统/UI框架/数据驱动引擎)
  ↑                    ↑
百草可食 Core         严生 Core
(草药/药理)           (体温/水分/医疗)
```

**优点：** 最干净的架构。
**缺点：** 拆分成本太高，而且百草可食的用户不需要一个没有草药内容的空壳库。不推荐现在做。

### 我的推荐：模式 B

理由：

1. **"硬核"指的是生存条件的严苛性** — 你自己说了。那么体温、水分、医疗、营养严化都属于"严苛生存"，不属于"草药学"。

2. **草药联动是桥接，不是核心** — 百草可食的五味七情/药性回旋是草药系统的核心玩法。硬核生存模组需要的是"吃了寒性草药体温下降"这种桥接效果，而不是重新实现一套药理。所以桥接层只需要：
   - 读取百草可食的 `HerbcraftDataAPI.nature(item)` 获取温度/五味
   - 根据温度调整硬核模组的体温值
   - 根据五味调整硬核模组的某些状态
   
3. **Homeostatic 的代码可以参考** — Homeostatic 已经做了体温+水分。你可以：
   - 研究 Homeostatic 的数据格式和 API
   - 借鉴其体温/水分的 tick 逻辑
   - 但用自己的 UI 和数据驱动架构（因为你的 UI 要改成数据驱动的）

4. **医疗系统需要新物品** — 芦荟、车前子等药材物品应该属于硬核模组自己注册，不属于百草可食。百草可食的 96 种草药是 Minecraft 原版植物，硬核模组可以加自己的药用植物。

### 健康磁条的具体设计

你提到了"隐形的健康磁条，滑块类型，曲线上有锚点"。具体化：

```
健康值 = f(营养平衡度, 体温稳定度, 水分充足度, 中毒史, 药物史, 时间衰减)

计算公式概念：

base_health = 50  (起始值)

// 营养平衡度贡献 (±20)
nutrition_score = 计算五维平衡度 → -20..+20

// 体温稳定度贡献 (±15)
temperature_score = 体温在正常区间的持续时间 → -15..+15

// 水分充足度贡献 (±10)
hydration_score = 水分在正常区间的持续时间 → -10..+10

// 负面历史惩罚 (-0..30)
penalty = (近期中毒次数 × 3) + (近期 debuff 累计时间 / 1200) → 0..30

// 药物正面历史 (+0..15)
medicine_bonus = 成功使用药物/稳定药性次数 → 0..15

health = clamp(base_health + nutrition_score + temperature_score 
         + hydration_score - penalty + medicine_bonus, 0, 100)

曲线可视化：

  100 ┤                                    ╭── 强健
   80 ┤                              ╭─────╯
   60 ┤                        ╭─────╯         ← 健康
   50 ┤──── 基准线 ────────────╯
   40 ┤                  ╭─────╯               ← 亚健康
   20 ┤            ╭─────╯
    0 ┤────────────╯                           ← 重病
      └──────────────────────────────────────
        时间 →
```

## 第四个问题：cocoa_fat 的定位

理解了 — cocoa_fat 从来不是一个确定要实现的第六维度。它只是文档里用来说明"如果加第六维度的话"的占位符。

**结论：** 不再把 cocoa_fat 当做一个计划中的特性。如果硬核模组最终需要新维度，候选应该根据游戏性设计来定，而不是占位符。比如：

| 候选维度 | 游戏性意义 | 是否必要 |
|---|---|---|
| `fiber` / 纤维 | 植物纤维摄入，影响消化/体力恢复 | 可选 |
| `hydration` / 水分 | 独立水分系统 | 如果做水分系统就需要 |
| `vitality` / 活力 | 综合健康指数，替代独立维度 | 可能不需要独立维度 |

但这些都是硬核模组的设计问题，不是百草可食 1.1.3/1.2.0 的任务。

| 议题 | 结论 |
